# Exercise 05 evidence: investigate a DNS or TLS failure

## 1. Setting and prediction

This is the supplied simulation from the Ex05 brief. It is not my real system. The hostname `site.lab.example`, the IP addresses, and every command output below are invented for the lab. I did not run any of these commands. I did not touch the DNS records or certificate for my real domain.

The scenario: `site.lab.example` should reach a new Railway deployment. The Railway URL `current-app.up.railway.app` already returns the current page and database content. Cloudflare is authoritative for `lab.example`, and the site's record is DNS only.

The failed check is an HTTPS request to the site name: `curl -Iv https://site.lab.example/`.

My prediction for a healthy setup: DNS should send `site.lab.example` to Railway, curl should connect to a Railway address, the certificate should be issued to `site.lab.example`, and the response should be `HTTP/2 200`.

## 2. Failed check and evidence

Date written: 2026-10-13. Everything in this section is **simulated output supplied by the brief**.

The zone still held the old Azure record:

```text
site.lab.example.  300  IN  A  198.51.100.24
```

DNS check (simulated):

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24
```

HTTPS check (simulated):

```text
$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

## 3. Diagnosis

I traced the request in order.

**DNS.** The name resolves, so DNS itself is working. The problem is where it points. The A record still sends `site.lab.example` to `198.51.100.24`, which is the old Azure server. The TTL is 300 seconds, so resolvers would only hold that answer for about five minutes. This is not a stuck cache. The record itself is wrong.

**Connection.** curl connected to `198.51.100.24` on port 443 with no timeout or refusal. So something is listening on the old server, and the network path works.

**TLS.** The old server presented a certificate for `old-vm.lab.example`. The browser asked for `site.lab.example`, so the names do not match and curl refuses it. That certificate is doing its job correctly for its own name. It is just the wrong server for this name.

**Which fault came first.** The DNS fault came first. The TLS error is a symptom of it. If the name had pointed at Railway from the start, the certificate would never have come from the old VM.

**What is still uncertain.** I only have one DNS answer, and I do not know which resolver gave it. I also do not know if the old VM still serves old content behind that certificate. A fix on the old server, like installing a certificate for `site.lab.example` there, would clear the TLS error but would still show the old site. That is why I would not treat this as a certificate problem.

## 4. Repair and repeated check

**My proposed repair.** In Cloudflare, delete the old A record and create a CNAME for `site.lab.example` pointing at `current-app.up.railway.app`, set to DNS only. A name cannot hold both an A record and a CNAME, so the A record has to go. Then wait out the 300 second TTL and repeat the same two checks. The ownership TXT record is already verified, so I expect Railway to answer for the custom name.

**The repeated check.** Again, **simulated output supplied by the brief**. I interpreted it. I did not run it.

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

**What changed.** The A record to `198.51.100.24` was replaced by a CNAME to `current-app.up.railway.app`, which resolves to `203.0.113.44`. The connected address changed from the old Azure IP to the Railway IP. The certificate subject changed from `old-vm.lab.example` to `site.lab.example`. Verification now passes and the response is `HTTP/2 200`.

**Compared with my proposal.** It matches. The one record change was the DNS fix I proposed, and the TLS error went away without any certificate work, which supports my reading that DNS was the first fault and TLS was the symptom. I do not need to revise the diagnosis.

**Limit of this evidence.** A `200` on a `curl -I` request shows the name, certificate and Railway front end line up. It does not prove the database content shows on the page. I would open the page and check the content before calling it done.

## 5. What I learned

One other check that separates the layers is `openssl s_client -connect IP:443 -servername site.lab.example`. I give it the IP directly, so DNS is out of the picture. It prints the certificate the server presents for that name and stops before any HTTP request, so the application is out of the picture too. If the certificate is wrong, it is a TLS or routing problem at that server. If the certificate is right but the page is broken, the problem is higher up in the application.

If the failure were still there after the change, I would first run `dig` against a second resolver, for example `dig @1.1.1.1 site.lab.example`, to see whether resolvers disagree, and wait past the TTL before judging.

A related real case from my own work is in `docs/how-this-site-is-secured.md`: my Cloudflare records were set to Proxied, which would have shown visitors Cloudflare's certificate instead of mine, so I switched them to DNS only before requesting my certificate.
